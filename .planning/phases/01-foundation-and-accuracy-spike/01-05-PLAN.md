<decisions_recorded_by_planner>
1. Debug view: part of the real app, shown when the address has `?debug=1`. Without the flag the user gets the camera picture and the status badge only.
2. Developer switches are URL parameters, read once at startup: `debug=1`, `model=heavy` (default `full`), `camera=rear` (default front), `delegate=gpu` (default CPU).
3. Running mode: the live loop uses `VIDEO`. The adapter exposes `setRunningMode` so plan 01-06 can switch to `IMAGE` for a captured burst.
4. Target rate for the live loop: 12 frames per second, with a skip when the previous inference has not finished.
5. Display mirroring: on by default for the front camera, off for the rear camera, toggled by a button. It is applied on the canvas context at draw time and nowhere else.
6. The WASM and model addresses are built in `src/main.js` from `document.baseURI`, so they are relative to the page and work on Vite and on a plain static server.
7. Start camera control (added at plan revision, 2026-10-03): exactly one of `btn-camera-start` and `btn-camera-stop` is visible. Start shows whenever the camera is stopped for any reason, so a hidden tab or a locked phone screen never forces the user back to the height form. The camera never restarts by itself when the tab becomes visible again; restarting needs the user's press (privacy and iOS gesture rules). PROTOCOL.md (plan 01-04) tells the session to set Auto-Lock to its longest setting.
8. `nextVideoFrame(videoEl, timeoutMs = 1000)` resolves `true` on the next presented frame or `false` after the timeout, and never rejects. Plan 01-06's capture uses the `false` result to stop a burst when the camera stops or the tab is hidden.
