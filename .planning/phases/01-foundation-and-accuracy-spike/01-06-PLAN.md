1. Bust row (user decision at plan approval, 2026-10-03, replacing a fixed 28% level): a band from `BUST_BAND_MIN_FRAC = 0.22` to `BUST_BAND_MAX_FRAC = 0.36` of the way from the shoulder-landmark midpoint to the hip-landmark midpoint. Inside the band each view uses the mask row whose midline run is widest; ties keep the highest row. The midline at a row is the line from the shoulder midpoint to the hip midpoint, evaluated at that row. The band justification and the reason the side view picks its own row are in plan 01-04 decision 7 and `validation/DEFINITIONS.md`. Frozen for this phase with the pass criteria; not a URL parameter, so it cannot be tuned on the test subjects.
2. Scale extent: head top and sole are the first and last mask rows that contain the body, converted to image pixels; the extent is `bottom - top + 1` rows.
3. A frame is refused with `body-touches-edge` when the silhouette touches the first or last mask row. This is the one validity check in Phase 1; the real quality gates are Phase 3.
4. Capture: 5 second delay, then 15 frames in `IMAGE` mode, at least 8 usable, median and median absolute deviation per value. The delay is a debug-view convenience so a person can step back; it is not the v2 countdown feature (CAPT-10) and has no sound.
5. Readings are shown with one decimal through `formatNumber`. They are held in memory until Clear readings or a reload. There is no export.
6. The live panel calls `measureView(obs, "front", heightCm)` whatever way the person faces, and labels the second value "Silhouette extent at bust level".
7. Arms-merged flag: a front reading whose bust row has fewer than three runs (arm, torso, arm) is flagged with `debug.reading.arms-merged`. The width is still reported and is inflated, so the flag is the warning. The side view is not flagged.
8. Developer labels: the bust row fraction is shown with the English developer label `bust row` and two decimals, like `cm/px`; no dictionary key is added.
9. Capture abort: `capture()` takes a token from a module-level counter, and `stopCamera()` (which runs on Stop camera, Change height, `pagehide` and a hidden tab) increments the counter, so a running countdown or burst sees a changed token and stops. The burst also stops when `nextVideoFrame` returns `false` (its 1000 ms timeout, plan 01-05). An aborted capture keeps no numbers, writes `t("debug.capture.failed", { reason: t("camera.status.stopped") })`, re-enables the buttons, and restarts the frame loop only if `camera.isRunning()`. The burst reads the height once at its start and a height change aborts it, so one reading never mixes two heights.
