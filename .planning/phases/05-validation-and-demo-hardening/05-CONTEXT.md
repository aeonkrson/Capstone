# Phase 5: Validation and Demo Hardening - Context

**Source:** Planner decisions (no discuss-phase run). User instruction at planning: no questions, working prototype, no design work (no CSS changes), be honest about what needs people and devices.

## Phase Boundary

In scope: rescan (MEAS-09), the accuracy study tooling and its honest evaluation (ACC-01..03), demo hardening that code can do (production build served over HTTPS on the LAN, startup check, debug frame rate), checklists for the human sessions, and closing out stale docs from earlier phases.

Not doable by an agent: tape measuring team members, real iPhone / Android / laptop runs, recording the fallback demo video. These become ready-to-run checklists with every result cell left as `not run`. No measurement, device result or verdict is invented.

## Decisions

- **D-01 Rescan entry.** A `Scan again` button (`#btn-rescan`) in `#body-section`, shown only when at least one saved measurement exists. It opens `#scan-area`, and reuses the Phase 4 path: consent (in memory per page load), height (in memory, re-asked after a reload), guided scan, review. If the camera is already running it restarts the guided scan.
- **D-02 Replace semantics.** Saving a review is a whole new scan: all five measurement keys are replaced. An optional key left empty (waist, arm) is cleared, so no value from an older scan survives next to the new ones. History entries are kept (they are past checks). The on-screen fit result is cleared and re-run by the user. New pure function `applyRescan` in `src/core/profileState.js`; `applyReview` stays as is for its existing tests.
- **D-03 Replace notice.** The review screen shows a one-line note when saved measurements exist ("Saving replaces your saved measurements"), and the saved status says the old measurements were replaced.
- **D-04 Study data file.** New `validation/study-readings.csv`, header `subject,device,browser,measurement,repeat,tape1_cm,tape2_cm,scan_cm,notes`. Device is `iphone`, `android` or `laptop`; the `phone` class is iphone plus android. Subject is `S1`..`S9` (anonymous, same scheme as Phase 1 and 3). Measurement is `shoulder`, `chest`, `waist`, `torso`, `arm`. `scan_cm` is the value shown on the review screen before any edit. Phase 1 `readings.csv` and Phase 3 `phase3-readings.csv` and their scripts are not changed.
- **D-05 Targets and verdicts.** Per device class (phone, laptop): shoulder mean absolute error <= 2.5 cm (ACC-01); chest mean absolute error <= 3.5 cm (ACC-02); size agreement: for every subject the app's recommended size (`recommendSize(chest, "regular", CATALOG[0].chart)` from `src/core/fit.js`) from the scan chest equals the one from the tape chest, or the scan result is borderline with the tape size as its neighbour (ACC-02). At least 2 subjects per device class, else that class is INSUFFICIENT DATA. Overall: INSUFFICIENT DATA if either class is insufficient; GO if all three targets are met on both classes; CONDITIONAL if all three are met on one class; NO-GO otherwise. Targets are exported constants; a revised target needs a dated line in `validation/GO-NO-GO.md` and a constant change, never an edit of the results file.
- **D-06 Results file.** `validation/STUDY-RESULTS.md` is generated by `node validation/study.mjs --write` and is never edited by hand. With no data rows every cell reads `no data` and the overall outcome is `INSUFFICIENT DATA`.
- **D-07 Photos and videos stay out of the repo.** `.gitignore` gets repo-wide image and video patterns and a `recordings/` folder for the fallback demo video. A test fails if git tracks any image or video file.
- **D-08 Demo build.** `npm run build` also copies `vendor/mediapipe/wasm/` and `vendor/mediapipe/models/` into `dist/vendor/mediapipe/` (the bundle is imported and bundled, but the wasm and model files are fetched at runtime and are missing from `dist/` today) and checks their SHA-256 against `vendor/mediapipe/SHA256SUMS`. `npm run demo` builds and serves `dist/` with `vite preview --host`; `@vitejs/plugin-basic-ssl` 2.3.0 already sets `preview.https` (checked in its dist source).
- **D-09 Startup check.** Pure `src/core/preflight.js` returns issue codes for a missing secure context, missing camera API and missing WebAssembly. `src/main.js` shows them in `#preflight-status` at the top of the scan area with a pointer to manual entry. Being offline is not an issue: every file is same-origin and nothing is fetched from the internet.
- **D-10 Frame rate readout.** Debug only (`?debug=1`): an `fps` line in the existing engine info list, computed by a pure helper from frame timestamps. Debug labels stay untranslated like the existing `inference ms`.
- **D-11 Human sessions.** Every human step is a checklist with `not run` results: the Phase 5 study protocol, the full-flow device run (iPhone, Android, laptop), and the fallback demo recording. Requirements ACC-01..03 stay pending in REQUIREMENTS.md until real data exists. MEAS-09 stays pending until the device run confirms rescan on a real camera (code and flow tests done).
- **D-12 HUMAN-TODO.md at the repo root** lists every outstanding human step in the order to do them.
- **D-13 CLAUDE.md** stack, conventions and architecture sections are regenerated from rewritten `.planning/codebase/*.md` files with `node $HOME/.claude/get-shit-done/bin/gsd-tools.cjs generate-claude-md`; the GreenWear text is removed.
- **D-14 No design work.** `css/` is not touched. New markup is plain elements with ids, no new classes.
